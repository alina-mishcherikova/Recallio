# Recallio — Architecture

**Status:** Approved decisions applied — awaiting final approval · **Date:** 2026-11-08 · **Spec:** [`docs/spec.md`](./spec.md) (v1.1)

This document describes how Recallio is built: the stack, the code structure, the data model, the
rules that protect FSRS scheduling, and the development workflow (agents, git, quality gates).
Decisions are recorded in §12. Hosting is the only open question left.

---

## 1. Stack

| Concern          | Choice                                                      | Why                                                                                     |
| ---------------- | ----------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Framework        | **Nuxt 4** (Vue 3, TypeScript strict)                       | One full-stack app. UI and API share types and validation.                              |
| Backend          | **Nitro server routes** (`server/api/**`)                   | Built into Nuxt, so there is no second server to maintain.                              |
| Runtime          | **Node.js ≥ 24** (local: 25.4)                              | Required by `ts-fsrs` v6.                                                               |
| Database         | **PostgreSQL 17** (Docker locally, managed in prod)         | Transactions, row locks, and constraints are needed for SRS integrity.                  |
| ORM / migrations | **Drizzle ORM + drizzle-kit**                               | Typed SQL with SQL-first migrations.                                                    |
| Validation       | **Zod** in `shared/`                                        | One schema per payload, used on both client and server.                                 |
| Auth             | **nuxt-auth-utils**                                         | Sealed cookie sessions, scrypt password hashing (`hashPassword`), `requireUserSession`. |
| Scheduling       | **ts-fsrs v6** (FSRS-7 default), version pinned exactly     | Established implementation, deterministic when fuzz is disabled.                        |
| CSV              | **papaparse**                                               | Handles delimiter detection, quoted fields, and UTF-8.                                  |
| UI               | **Nuxt UI v4** (Tailwind CSS v4)                            | Accessible primitives (Reka UI), responsive, keyboard-friendly.                         |
| Security headers | **nuxt-security**                                           | CSP, HSTS, X-Frame-Options, request size limits, rate limiting (§8).                    |
| Tests            | **Vitest** (`@nuxt/test-utils`) + **Playwright**            | Unit, integration (real Postgres), and E2E/responsive tests.                            |
| Lint / format    | **ESLint (`@nuxt/eslint`) + Prettier**, `vue-tsc` typecheck | Run by hooks and CI.                                                                    |
| CI               | **GitHub Actions**                                          | Lint, typecheck, tests on every PR.                                                     |

## 2. Repository structure

```
app/                         # Nuxt 4 client (srcDir)
  pages/                     # routes: /login, /dashboard, /collections/[id], /review, /practice/typing, /practice/mcq ...
  components/                # UI, grouped by domain: collections/, vocabulary/, review/, practice/, ui/
  composables/               # useReviewSession, usePracticeSession, useAnswerFeedback ...
  layouts/  middleware/      # auth middleware, app shell
server/
  api/                       # thin HTTP handlers: parse input (Zod) → call service → return DTO
    auth/  collections/  vocabulary/  import/  review/  practice/  analytics/
  services/                  # business logic, one folder per domain module
    srs/                     # THE ONLY module allowed to write srs_* tables (§5)
    practice/  vocabulary/  collections/  import/  analytics/
  db/
    schema/                  # Drizzle tables, one file per domain
    migrations/              # generated by drizzle-kit, committed
    client.ts
  utils/                     # requireOwner(), rate limiting, error helpers
shared/                      # code imported by BOTH app/ and server/ (Nuxt 4 `shared/` dir)
  schemas/                   # Zod request/response schemas
  answers/                   # normalization + diff engine (pure, heavily unit-tested)
  types/  constants/         # Direction, ExerciseType, event names
tests/
  unit/  integration/  e2e/
docs/                        # spec.md, architecture.md, decisions/ (ADRs)
.claude/                     # agent workflow (§9)
```

**Layering rule:** `api` → `services` → `db`. Handlers never touch the database directly. Services
never read `event`/HTTP objects. Pure logic, such as answer checking and MCQ distractor filtering,
lives in `shared/` or in pure service functions so it can be unit-tested without a database.

## 3. Domain modules (MVP)

| Module        | Responsibility                                                                             | Issues          |
| ------------- | ------------------------------------------------------------------------------------------ | --------------- |
| `auth`        | Register, login, logout, session, account deletion                                         | LEX-003         |
| `collections` | Language-pair collections. Languages are immutable once entries exist (DEC-001).           | LEX-004         |
| `vocabulary`  | Entries, meanings, accepted answers, answer change log. Creates the 2 SRS cards per entry. | LEX-005         |
| `import`      | CSV parse → column mapping → preview → duplicate resolution → commit                       | LEX-006         |
| `srs`         | FSRS scheduler wrapper, due queue, review submission                                       | LEX-007/008/009 |
| `practice`    | Answer validation, Typing, Multiple Choice, practice attempts                              | LEX-010–013     |
| `analytics`   | Read-only aggregates over the separate activity tables                                     | LEX-014         |

Release 2 and 3 modules (`context`, `listening`, `tests`, `guided`) follow the same pattern. They are
practice-type modules, so they get **no** write access to SRS.

## 4. Data model

Spec §14 is the baseline. The additions below are needed to meet the acceptance criteria.

```
users(id uuid pk, email citext unique, password_hash, native_language,  -- languages: ISO 639-1 daily_new_limit int default 20,
      daily_review_limit int default 200, timezone text, created_at, deleted_at)
collections(id, owner_id → users, title, native_language, target_language, description, topic,
            normalization jsonb, archived_at, created_at)          CHECK native_language <> target_language
vocabulary_entries(id, collection_id, target_expression, native_expression, part_of_speech, topic,
                   revision int, created_at, updated_at)
vocabulary_meanings(id, entry_id, definition, grammatical_metadata jsonb)
accepted_answers(id, entry_id, meaning_id null, language, answer_text, normalized_text, is_primary)
answer_change_log(id, answer_id, entry_id, user_id, action, before jsonb, after jsonb, created_at)   -- US-VOC-04
answer_flags(id, user_id, entry_id, direction, submitted_answer, status, created_at)                  -- US-TYP-03

srs_cards(id, user_id, entry_id, direction, state, due_at, stability, difficulty, elapsed_days,
          scheduled_days, learning_steps, reps, lapses, last_review_at, scheduler_version, updated_at)
          UNIQUE(user_id, entry_id, direction)
srs_review_logs(id, card_id, client_review_id uuid UNIQUE, rating, reviewed_at, previous_state jsonb,
                next_state jsonb, previous_due_at, next_due_at, scheduler_version)

practice_attempts(id, user_id, entry_id, exercise_type, direction, source_mode, submitted_answer,
                  matched_answer_id, is_correct, diff jsonb, session_id, created_at)
```

- **Languages** are stored as ISO 639-1 codes (`fr`, `en`, ...), validated against an allow-list in
  `shared/constants/languages.ts`. The launch allow-list is **`fr` and `en`**. Adding a language
  means adding it to that list, with no schema change.
- **Direction** is an enum: `recognition` (target → native) and `production` (native → target).
- **Normalization config** is stored per collection, with defaults for case, accents, punctuation,
  and whitespace (US-VOC-04).
- **Content revisions:** review and attempt rows store what was shown and answered, so editing an
  entry never rewrites history. A "materially different meaning" edit goes through an explicit
  `resetCards` action (US-VOC-02).
- **Deleting a collection** is a soft archive by default. Hard delete requires confirmation and
  cascades.
- Release 2/3 tables (`sentence_examples`, `sentence_templates`, `guided_sessions`,
  `guided_session_entries`, `assessment_results`, `test_sessions`) will be added in their own
  migrations. None of them has a foreign key that writes to `srs_*`.

## 5. SRS isolation — the non-negotiable rule (DEC-002, US-SRS-03)

Enforced at four layers, so a mistake in one layer is caught by another:

1. **Module boundary.** Only `server/services/srs/review.service.ts` imports the write helpers for
   `srs_cards` and `srs_review_logs`. An ESLint `no-restricted-imports` rule fails the build if any
   other file imports `server/db/schema/srs` write paths.
2. **Single endpoint.** `POST /api/review/submit` is the only route that calls `submitReview()`.
   Practice endpoints (`/api/practice/**`) have no code path to it.
3. **Database guard.** A Postgres trigger rejects `UPDATE` on `srs_cards` scheduling columns unless
   a `srs_review_logs` row is inserted in the same transaction (via the transaction-local setting
   `app.review_id`). Card creation (insert) is allowed for the vocabulary service.
4. **Regression tests.** Every practice mode has an integration test that snapshots `srs_cards`
   and `srs_review_logs`, runs practice attempts, and asserts both are unchanged.

**Review submission flow (atomic and idempotent):**

```
client → POST /api/review/submit { clientReviewId (uuid v7), cardId, rating, reviewedAt }
  BEGIN
    SELECT card FOR UPDATE WHERE id = cardId AND user_id = session.user  -- ownership + row lock
    if srs_review_logs has clientReviewId → return the stored result (idempotent replay)
    next = fsrs.next(card, reviewedAt, rating)   -- pure, deterministic
    INSERT srs_review_logs (...)                 -- UNIQUE(client_review_id) blocks races
    UPDATE srs_cards SET ...next
  COMMIT
```

**FSRS configuration:** `ts-fsrs` is pinned to an exact version. `request_retention = 0.90`,
`enable_fuzz = false` (spec §15 requires deterministic scheduling), and `scheduler_version`
(for example `ts-fsrs@6.0.0/fsrs-7`) is stored on every card and log. Upgrading the scheduler means
bumping the version string. Existing cards keep their history and switch to the new scheduler on
their next review.

**Workload limits (US-SRS-04):** limits only cap _how many cards are served per day_. Overdue cards
stay due and are never auto-completed. The dashboard shows `due total` vs. `remaining today`.
"Today" is calculated in the user's time zone.

## 6. Answer validation engine (`shared/answers`, LEX-010)

Pure TypeScript, shared by Typing, MCQ, and the later Context and Listening modes:

1. `normalize(text, rules)`: Unicode NFC, trim, collapse whitespace, then optional case fold,
   accent strip, and punctuation strip, per the collection's rules.
2. `check(submitted, acceptedAnswers, rules)` returns `{ isCorrect, matchedAnswerId, closest, diff }`.
   An answer is correct only if it matches a stored accepted answer exactly after normalization.
   Unknown answers are never auto-accepted (US-TYP-03).
3. `diff(submitted, closest)` uses a character-level Levenshtein alignment that produces
   `match | wrong | missing | extra` segments. The UI renders each kind with a distinct text
   decoration and a screen-reader label, so feedback never relies on color alone (US-TYP-02).

**MCQ generator (LEX-012):** distractors come from the same collection, are in the answer language,
and share the part of speech where possible. Any candidate that shares a normalized accepted answer
with the correct entry is excluded. Options are shuffled. If there are fewer than 3 valid
distractors, the question is skipped instead of degraded.

## 7. Activity and event taxonomy

Activity types are kept separate in storage (spec §12):

| Event                       | Table                                                | Written by                                                          |
| --------------------------- | ---------------------------------------------------- | ------------------------------------------------------------------- |
| `review_completed`          | `srs_review_logs`                                    | `srs` module only                                                   |
| `practice_answer_submitted` | `practice_attempts`                                  | `practice` module (`source_mode` = typing, mcq, difficult_words...) |
| `test_completed`            | `assessment_results` (R2)                            | `tests` module                                                      |
| `guided_stage_completed`    | `guided_session_entries` / `assessment_results` (R3) | `guided` module                                                     |

Every row records the source mode, exercise type, direction, timestamp, and outcome. Analytics only
reads, and labels practice accuracy and FSRS retention as different metrics.

## 8. Security (OWASP), privacy, accessibility

**Target:** [OWASP Top 10 (2025)](https://owasp.org/Top10/) fully covered, with
[OWASP ASVS 5.0](https://owasp.org/www-project-application-security-verification-standard/)
**Level 2** as the verification checklist. Every PR is checked against this section by the
`security` agent (§9).

| OWASP risk                        | Controls in Recallio                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A01 Broken Access Control**     | Every service takes `userId`. Queries are scoped by owner through `collections.owner_id` or `user_id`. The `requireOwner()` helper returns 404 (not 403) for other users' resources. Deny by default: all `/api/**` routes require a session except an explicit public allow-list (`/api/auth/register`, `/api/auth/login`). Integration tests check that user B can't access user A's data on every route (IDOR tests). UUIDs are used, but ownership checks never rely on IDs being hard to guess. |
| **A02 Security Misconfiguration** | `nuxt-security` sets a strict CSP (no `unsafe-inline` scripts, nonces), HSTS, `X-Content-Type-Options`, `Referrer-Policy`, `frame-ancestors 'none'`, and a `Permissions-Policy`. Production builds have no stack traces, no source maps served publicly, and no devtools. CORS stays same-origin only. Secrets come only from env vars, validated at boot with Zod, and are never committed (`.env` is git-ignored, `.env.example` lists names only).                                                |
| **A03 Software Supply Chain**     | `pnpm` with a committed lockfile and exact versions for security-relevant packages (ts-fsrs, auth). CI runs `pnpm audit --prod` and fails on high/critical findings. Dependabot handles updates, GitHub secret scanning and push protection are enabled, and GitHub Actions are pinned to commit SHAs. New dependencies need justification in the PR.                                                                                                                                                |
| **A04 Cryptographic Failures**    | Passwords are hashed with scrypt (nuxt-auth-utils `hashPassword`), never logged or returned. The session cookie is sealed (iron) with a random secret of 32+ chars, and is `HttpOnly`, `Secure`, `SameSite=Lax`. TLS everywhere in production, including the DB connection (`sslmode=require`). No sensitive data in URLs or localStorage.                                                                                                                                                           |
| **A05 Injection**                 | Drizzle uses parameterized queries only. Raw `sql` templates must use bound parameters, and `sql.raw()` is banned by a lint rule. Zod validates every body, query, and route param (types, lengths, enums, `strict()` to reject unknown keys). Vue escapes output by default, and `v-html` is banned by a lint rule. CSV cells starting with `= + - @` are neutralized on any future export (formula injection).                                                                                     |
| **A06 Insecure Design**           | Threat model per epic (written by `architect`). SRS isolation is enforced in four layers (§5). Business limits (daily limits, import caps) are enforced server-side. Destructive actions need confirmation and re-checked ownership.                                                                                                                                                                                                                                                                 |
| **A07 Authentication Failures**   | Password policy follows NIST 800-63B: at least 12 chars, up to 128, no composition rules, checked against a common-password list. Login is rate-limited per IP and per account, with exponential backoff. Login and register return generic errors so they don't reveal which emails exist. The session is rotated on login and destroyed on logout. Idle timeout is 7 days and absolute timeout is 30 days.                                                                                         |
| **A08 Software / Data Integrity** | CSRF: `SameSite=Lax` cookie, plus an `Origin`/`Sec-Fetch-Site` check on every mutating request, plus a CSRF token (`nuxt-security` CSRF). Review submissions are idempotent (`clientReviewId`). DB constraints and the trigger protect SRS integrity. Migrations are reviewed in PRs and never edited after merge.                                                                                                                                                                                   |
| **A09 Logging & Alerting**        | Structured JSON logs record auth successes and failures, access-denied events, rate-limit hits, import results, and account deletion, each with the user id and a request id. Passwords, session tokens, cookies, and full request bodies are never logged.                                                                                                                                                                                                                                          |
| **A10 Exceptional Conditions**    | A central error handler maps errors to safe messages (`{ statusCode, message }`) with no internals. Transactions roll back on any error, and the default is fail-closed: if an ownership or validation check throws, the request is denied. Timeouts and limits apply to DB queries, body size (1 MB, 5 MB for CSV), and CSV row count (10,000).                                                                                                                                                     |

**Also part of secure coding:**

- **Abuse protection:** per-user and per-IP rate limits on auth, review, practice, and import endpoints.
- **Least privilege:** the app's DB role can't run DDL. Migrations run with a separate role in CI/deploy.
- **CSV import:** check MIME type and extension, enforce UTF-8, never execute or eval content, and
  treat every cell as plain text.
- **Account recovery:** email verification and password reset are **out of MVP scope** (decision
  2026-11-08). Accepted risk: a user who forgets their password can't recover the account. This is
  documented in the README and is planned for a later release.
- **Static checks in CI:** `eslint-plugin-security`, GitHub CodeQL, `pnpm audit`, gitleaks.

**Privacy (GDPR):** account deletion hard-deletes all user-owned rows in one transaction. Data
minimization: only email, password hash, and learning data are stored. Retention is documented in
`docs/privacy.md`.

**Accessibility:** WCAG 2.2 AA. Includes visible focus, keyboard shortcuts in Review (Space =
reveal, 1–4 = rating), touch targets of at least 44px, and `dvh`/`visualViewport` handling so inputs
stay visible above the mobile keyboard. axe checks run in Playwright.

## 9. Development workflow — agents

The main Claude session acts as the **orchestrator**. It reads an issue, calls the specialist agents
(`.claude/agents/*.md`), and stops at decision points to ask Alina.

| Agent       | Role                                                                                                            | Writes code?   |
| ----------- | --------------------------------------------------------------------------------------------------------------- | -------------- |
| `architect` | Turns an issue into a plan: files, schema changes, API contracts, tests, risks. Updates `docs/decisions/` ADRs. | No (docs only) |
| `backend`   | `server/**`, `shared/**`, Drizzle schema and migrations                                                         | Yes            |
| `frontend`  | `app/**`: pages, components, composables, accessibility                                                         | Yes            |
| `tester`    | Writes and runs Vitest/Playwright tests, reviews the diff for bugs and spec violations                          | Tests only     |
| `security`  | Reviews every diff against §8 (OWASP Top 10 / ASVS L2), runs audit tools, writes abuse-case tests               | Tests only     |
| `docs`      | README, CLAUDE.md, API docs, `docs/` after each feature                                                         | Docs only      |

**Flow per issue:**

```
issue LEX-xxx
  → architect: plan  ──► orchestrator shows plan to Alina if it involves a big decision
  → create branch  feat/lex-xxx-short-name
  → backend ∥ frontend   (parallel when files don't overlap; contract = shared/schemas)
  → tester: tests + review  ∥  security: OWASP review   ──► fix loop until green
  → docs: update docs
  → conventional commits → push → PR (Closes #n) → Alina reviews & merges
```

## 10. Git conventions

- **Branches** ([Conventional Branch](https://conventional-branch.github.io/)): `feat/`, `fix/`,
  `hotfix/`, `release/`, `chore/` + lowercase kebab-case, including the issue key.
  Examples: `feat/lex-004-collections-api`, `fix/lex-011-diff-accent-handling`,
  `chore/lex-017-ci-pipeline`.
- **Commits** ([Conventional Commits 1.0](https://www.conventionalcommits.org/)):
  `type(scope): summary`, with types `feat fix docs test refactor perf build ci chore style`. Scopes
  are module names (`auth`, `srs`, `practice`...). Footer: `Refs: LEX-004`. Use `!` /
  `BREAKING CHANGE:` when needed.
- **PRs:** one issue per PR, merged into `main` only after CI passes and Alina approves. Use squash
  merge so `main` history stays conventional.
- Enforcement: a commitlint + branch-name check in CI (added in LEX-001).
